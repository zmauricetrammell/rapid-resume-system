# RRS V3 Event Model

## Status

Draft V0.2 — FIX-007 applied

## Purpose

The Event Model defines how the V3 runtime records, normalizes, delivers, processes, retries, and audits events across internal runtime behavior and external integrations.

The event system connects:

- Runtime Job state.
- Professional artifact commits.
- Handler execution.
- Routing decisions.
- Trello projections.
- Discord human interaction.
- Manual runtime controls.
- Retry and recovery behavior.

Events describe facts that have already occurred.

Commands request actions the runtime intends to perform.

These concepts remain separate.

---

# Core Invariants

1. Events describe facts; commands request actions.
2. External provider payloads are normalized before core runtime processing.
3. One internal event envelope is used for runtime events.
4. Event delivery is at-least-once.
5. Event processing is idempotent.
6. Events are persisted before asynchronous processing.
7. Event payloads reference authoritative artifacts and interactions rather than embedding full professional state.
8. Professional artifact contents remain authoritative outside the event log.
9. Runtime ordering is required only where state safety demands it, primarily within one Runtime Job.
10. Trello is primarily a projection/consumer of runtime events.
11. Discord may produce human-input events but does not directly mutate professional evidence.
12. Failed events are retried or dead-lettered rather than silently dropped.
13. Integration-only failures do not roll back committed professional state.
14. Duplicate-event protection is reinforced by operation-key idempotency and atomic commits.
15. Event history is auditable.

---

# 1. Events vs Commands

## Event

An Event records:

> Something happened.

Examples:

```text
job_created
artifact_committed
execution_failed
routing_decided
human_input_received
job_completed
```

Events are historical facts.

## Command

A Command records:

> The runtime intends to perform an action.

Examples:

```text
schedule_operation
evaluate_routing
sync_trello
open_interaction
retry_execution
enter_manual_review
cancel_job
```

Commands may result from Events.

Example:

```text
artifact_committed
        ↓
command: evaluate_routing
```

Do not use Events as disguised commands.

---

# 2. Internal Event Envelope

All runtime and normalized external events use a common envelope.

```yaml
event:

  event_id: EVT-000123

  event_type: artifact_committed

  job_id: JOB-0001

  occurred_at: 2026-08-22T20:30:00-07:00
  received_at: 2026-08-22T20:30:01-07:00

  source:
    category: runtime
    provider: internal
    provider_event_id: null

  correlation_id: EXEC-0042
  causation_id: EVT-000122

  criticality: workflow_critical

  payload:
    artifact:
      artifact_type: job_experience_analysis
      artifact_id: JEA-0004
      artifact_version: 5

  processing:
    status: received
    attempt_count: 0
    last_error: null
    processed_at: null
```

---

# 3. Event Identity

Every normalized event receives:

```text
event_id
```

Example:

```text
EVT-000123
```

The Event ID is generated by the V3 runtime and is unique inside the runtime event store.

It is distinct from any provider-supplied event ID.

---

# 4. Provider Event Identity

External events should preserve provider identity.

Example:

```yaml
source:
  category: integration
  provider: trello
  provider_event_id: "abc123"
```

The combination:

```text
provider
+
provider_event_id
```

should be used for first-line external event deduplication.

If the provider does not supply a stable event ID, the adapter may derive a deterministic provider fingerprint from stable webhook fields.

---

# 5. Correlation ID

`correlation_id` groups related runtime activity.

Typical values may reference:

```text
execution_id
interaction_id
operation_key
runtime transaction ID
```

Examples:

```text
EXEC-0042
INT-0008
OPKEY-ABC123
```

Correlation supports debugging across multiple events.

---

# 6. Causation ID

`causation_id` identifies the Event that directly caused another Event.

Example:

```text
EVT-0101 artifact_committed
      ↓
EVT-0102 routing_decided
      ↓
EVT-0103 lifecycle_changed
```

Then:

```yaml
EVT-0102:
  causation_id: EVT-0101

EVT-0103:
  causation_id: EVT-0102
```

This creates a clear causal audit chain.

---

# 7. Event Source

Recommended source structure:

```yaml
source:

  category:
    enum:
      - runtime
      - integration
      - human
      - system

  provider:
    enum:
      - internal
      - trello
      - discord
      - manual
      - other

  provider_event_id: string | null
```

The provider list may expand without changing core event semantics.

Core runtime logic should react to normalized `event_type`, not provider-specific webhook shapes.

---

# 8. External Event Normalization

External payloads must be normalized immediately.

Example:

```text
Raw Trello webhook
       ↓
Trello adapter
       ↓
Normalized V3 Event
```

Example:

```text
Raw Discord gateway/interactions event
       ↓
Discord adapter
       ↓
Normalized V3 Event
```

Core routing and handler code must not depend on raw Trello or Discord JSON structures.

---

# 9. Persist Before Process

External event ingress should follow:

```text
Receive external event
        ↓
Validate basic envelope
        ↓
Normalize
        ↓
Deduplicate provider event
        ↓
Persist normalized Event
        ↓
Acknowledge provider
        ↓
Process asynchronously
```

Do not perform long-running professional operations synchronously inside webhook response handling.

This prevents:

- Provider timeout.
- Dangerous webhook redelivery.
- Lost events during application crashes.
- Coupling external service latency to agent execution.

---

# 10. At-Least-Once Delivery

V3 adopts:

> At-least-once Event delivery with idempotent processing.

Exactly-once delivery is not required.

Duplicate delivery is expected and safe.

Defense in depth:

```text
Provider event deduplication
+
Event processing deduplication
+
Operation-key idempotency
+
Atomic pointer commits
```

---

# 11. Event Processing State

Persisted Events maintain processing metadata.

```yaml
processing:

  status:
    enum:
      - received
      - processing
      - processed
      - ignored
      - retry_pending
      - dead_letter

  attempt_count: integer

  last_error:
    type: string | null

  processed_at:
    type: datetime | null
```

---

# 12. Processing Status

## `received`

Event is persisted and waiting for processing.

## `processing`

A worker currently owns processing.

## `processed`

Event completed successfully.

## `ignored`

Event was valid but intentionally required no runtime action.

Example:

```text
Trello card description changed
but no defined runtime control action occurred.
```

## `retry_pending`

Processing failed in a retryable way.

## `dead_letter`

Processing repeatedly failed or cannot be safely handled automatically.

---

# 13. Event Body Immutability

The logical Event body should be immutable after persistence.

Immutable fields include:

- `event_id`
- `event_type`
- `job_id`
- timestamps
- source
- correlation
- causation
- criticality
- payload

Processing metadata may change.

A future implementation may store processing status in a separate Event Processing record if stronger immutability is desired.

---

# 14. Event Criticality

V0.1 uses two criticality classes:

```text
workflow_critical
integration_only
```

## `workflow_critical`

Failure may prevent Runtime Job progress or safety.

Examples:

- Professional artifact commit event.
- Routing event.
- Handler scheduling event.
- Human investigation completion event.

Repeated failure may cause:

```text
health → blocked
lifecycle → manual_review
```

## `integration_only`

Failure affects an external projection or convenience integration but does not invalidate professional/runtime state.

Examples:

- Trello comment synchronization.
- Nonessential Discord status message.

Repeated failure normally causes:

```text
health → degraded
```

rather than rollback or manual review.

---

# 15. Event Payload Principle

Events carry references, not full professional artifacts.

Preferred:

```yaml
payload:

  artifact:
    artifact_type: job_experience_analysis
    artifact_id: JEA-0004
    artifact_version: 5
```

Avoid:

```yaml
payload:
  full_jea: ...
```

Consumers resolve the committed artifact from authoritative storage.

This ensures that:

- Event history stays compact.
- Consumers use exact committed state.
- Professional content is not duplicated.
- Artifact immutability remains centralized.

---

# 16. Interaction Payload Principle

Human-input Events reference Interaction and Message records.

Example:

```yaml
event_type: human_input_received

payload:
  interaction_id: INT-0004
  message_ref: MSG-0091
```

The full Discord message or transcript belongs in the Interaction store, not in the Event body.

The Event records that new human input exists.

---

# 17. Initial Event Vocabulary

V0.1 uses a small generic event vocabulary.

## Job Events

```text
job_created
job_completed
job_cancelled
```

## Operation / Execution Events

```text
operation_scheduled
execution_started
execution_committed
execution_failed
```

## Artifact Events

```text
artifact_committed
```

Use:

```text
payload.artifact.artifact_type
```

instead of defining separate events such as:

```text
jea_created
resume_created
erq_created
```

## Routing Events

```text
routing_decided
lifecycle_changed
```

`lifecycle_changed` means the Runtime Job lifecycle transition has already committed successfully.

It must be persisted transactionally with:

```text
routing_history append
+
lifecycle.phase update
+
lifecycle.entered_at update
+
Runtime Job revision increment
```

so downstream consumers cannot observe a lifecycle transition without its durable Event.

## Interaction Events

```text
interaction_required
interaction_started
human_input_received
interaction_paused
interaction_completed
```

## Health / Recovery Events

```text
health_changed
manual_review_required
retry_requested
cancel_requested
```

Additional Events should be added only when materially distinct semantics require them.

# 18. Initial Command Vocabulary

Commands should also remain generic.

Recommended V0.1 commands:

```text
schedule_operation
evaluate_routing
sync_trello
open_interaction
close_interaction
retry_execution
enter_manual_review
cancel_job
```

Example:

```yaml
command:
  command_type: schedule_operation
  job_id: JOB-0001

  payload:
    operation_type: generate_analysis
```

Avoid proliferation such as:

```text
schedule_generate_analysis
schedule_generate_resume
schedule_evaluate_resume
```

unless implementation evidence shows separate command types are useful.

```text
EVT-001
job_created
    ↓
CMD schedule_operation(generate_analysis)

EVT-002
execution_started

EVT-003
artifact_committed(JEA)
    ↓
CMD evaluate_routing

EVT-004
routing_decided

    ↓
CMD schedule_operation(request_evidence)

EVT-005
artifact_committed(ERQ)

EVT-006
routing_decided
evidence_request → investigation
    ↓

```

# 20. Internal Event Production

Runtime components emit Events after successfully completing meaningful runtime actions.

Examples:

## Handler

After successful professional commit:

```text
artifact_committed
execution_committed
```

## Router

After deriving a valid transition, the authoritative routing mutation persists:

```text
routing_decided
```

as routing history and persists:

```text
lifecycle_changed
```

as the durable Event announcing the committed lifecycle transition.

The lifecycle mutation and `lifecycle_changed` Event are committed in the same SQLite transaction. `routing_decided` is not a substitute for the lifecycle mutation itself.

## Interaction Manager

After an investigation begins:

```text
interaction_started
```

After human interaction yields completed professional output:

```text
interaction_completed
```

## Health Manager

After state change:

```text
health_changed
```

---

# 21. Routing Trigger Events

Events that should commonly cause:

```text
evaluate_routing
```

include:

```text
job_created
artifact_committed
execution_committed
interaction_completed
manual recovery action
```

Not every Event requires routing evaluation.

Example:

```text
sync_trello succeeded
```

does not require routing.

---

# 22. Per-Job Ordering

V3 does not require global Event ordering.

Different Jobs may process concurrently.

Within one Runtime Job:

> Pointer-mutating and lifecycle-mutating work must serialize or pass concurrency validation.

`job_id` is the natural partition/coordination key.

Possible implementations may use:

- Per-job async locks.
- Database advisory locks.
- Queue partitions.
- Optimistic Runtime Job revision checks.
- Other safe concurrency mechanisms.

The architecture does not require one specific implementation.

---

# 23. Event Ordering and Causality

`occurred_at` should not be treated as sufficient concurrency control.

Distributed provider clocks may differ.

Runtime correctness relies on:

- Current Runtime Job revision.
- Exact artifact versions.
- Execution input snapshots.
- Operation-key idempotency.
- Commit concurrency rules.

Causation/correlation are for audit and coordination, not professional freshness.

---

# 24. Duplicate External Event Protection

On ingress:

```text
provider + provider_event_id
```

is checked.

If already known:

```text
acknowledge duplicate
do not create another normalized Event
```

If provider identity is unavailable, an adapter may use a deterministic event fingerprint.

---

# 25. Duplicate Internal Event Processing

A normalized Event may be delivered to a worker more than once.

Before processing:

```text
event.processing.status == processed?
```

If yes:

```text
no-op / acknowledge
```

If a downstream command is emitted twice despite this protection, operation-level idempotency prevents duplicate professional execution.

---

# 26. Trello Role

Trello primarily consumes Runtime Job state and Events.

Preferred flow:

```text
Runtime Job changes
        ↓
runtime Event
        ↓
sync_trello command
        ↓
Trello projection updated
```

Trello list placement is not authoritative professional or runtime logic.

---

# 27. Trello Inbound Control

Arbitrary Trello card movement should not automatically redefine Runtime Job lifecycle.

Human-originated Trello actions should be limited to explicitly supported controls.

Potential supported commands:

```text
cancel_job
retry_execution
resume_manual_review
create/start_job
```

These should be normalized through the Trello adapter into explicit runtime Events/Commands.

Avoid:

```text
card dragged to Resume Production
→ blindly mutate lifecycle
```

---

# 28. Trello Routing Comment Projection

A `routing_decided` Event may cause a Trello comment.

Example:

```text
Routing decision · ROUTE-00018

Analysis → Resume Production

Basis: JEA-0007 v5

No unresolved Material Evidence Needs remain.
```

Failure to post the comment does not invalidate routing.

It is:

```text
integration_only
```

---

# 29. Discord Role

Discord is an external human interaction surface.

It legitimately produces human-input events.

Example:

```text
Discord message
      ↓
Discord adapter
      ↓
human_input_received
```

The Event does not directly update JER/JEA/ERESP state.

It feeds the active Interaction.

The Interviewer professional operation eventually produces a schema-conformant Evidence Response.

---

# 30. Discord Message Handling

Recommended flow:

```text
Discord provider message
        ↓
normalize/persist message in Interaction store
        ↓
emit human_input_received
        ↓
interaction processor
        ↓
continue professional Interviewer interaction
```

Events should reference:

```text
interaction_id
message_ref
```

rather than embed full human messages.

---

# 31. Interaction Completion

Discord or another human interface may indicate conversational completion.

However:

```text
interaction_completed
```

does not by itself modify professional evidence.

The relevant professional artifact must still:

```text
stage
validate
commit
```

through the normal execution model.

---

# 32. Event Retry

Event-processing retries operate independently from professional execution retries.

Example:

```text
artifact_committed Event processing fails
```

Retrying the Event does not necessarily re-run the professional task.

Instead it retries the missing downstream runtime action, such as:

```text
evaluate_routing
```

This distinction prevents unnecessary professional re-execution.

---

# 33. Retry Policy

Retry policy is configuration.

Suggested conceptual policy:

```yaml
event_retry_policy:

  workflow_critical:
    max_attempts: 5

  integration_only:
    max_attempts: 10
```

Actual values should be configurable.

After exhaustion:

```text
workflow_critical
→ dead_letter
→ health blocked / manual review when Job progress is affected

integration_only
→ dead_letter
→ health degraded
```

---

# 34. Dead Letter

Events that cannot be processed safely become:

```text
dead_letter
```

Dead-letter Events remain inspectable.

A dead-letter record should preserve:

- Event ID.
- Job ID.
- Event type.
- Attempt count.
- Last error.
- First failure timestamp.
- Last failure timestamp.
- Criticality.
- Correlation/causation.

Do not silently delete failed Events.

---

# 35. Manual Review Trigger

A workflow-critical dead-letter Event may emit:

```text
manual_review_required
```

when automatic progress is unsafe.

This may transition:

```text
health → blocked
lifecycle → manual_review
```

according to Runtime Job and Routing rules.

---

# 36. Event Failure Example — Workflow Critical

```text
artifact_committed(JEA)
        ↓
evaluate_routing command
        ↓
router processing repeatedly fails
        ↓
Event dead_letter
        ↓
health → blocked
manual_review_required
```

Professional JEA remains committed.

The failure is in control-plane progression.

---

# 37. Event Failure Example — Integration Only

```text
routing_decided
        ↓
sync_trello
        ↓
Trello unavailable
        ↓
retry
        ↓
dead_letter
```

Result:

```text
Runtime Job routing remains valid.
Professional state remains valid.
health → degraded
```

No professional rollback occurs.

# 38. Event Store

The Event Store should support queries such as:

```text
Show all Events for JOB-0001.

What caused this lifecycle transition?

Which Event scheduled EXEC-0042?

Which Event opened INT-0008?

Which provider webhook caused this runtime action?

Which Events are dead-lettered?

Which integration projections are degraded?
```

Exact storage technology is not defined here.

---

# 39. Command Handling

Commands should have their own identity.

Recommended conceptual shape:

```yaml
command:

  command_id: CMD-00042

  command_type: schedule_operation

  job_id: JOB-0001

  created_at: ...

  causation_event_id: EVT-000123

  payload:
    operation_type: generate_analysis
```

Commands may also require idempotency depending on type.

For professional operations, the Artifact and Execution Commit Model's `operation_key` remains the authoritative logical execution guard.

---

# 40. Commands Are Not Historical Truth

Unlike Events, Commands represent requested actions.

A Command may:

```text
succeed
fail
be cancelled
be deduplicated
become obsolete
```

The resulting Event records what actually happened.

Example:

```text
CMD schedule_operation(generate_analysis)
        ↓
execution begins
        ↓
EVT execution_started
```

# 44. Event Versioning

The Event envelope should include a schema/version identifier once formalized.

Example:

```yaml
event_schema_version: "3.0"
```

Adapters must normalize provider payloads into the current supported Event schema.

Backward compatibility rules should be introduced when multiple Event schema versions exist.

---

# 45. Event Security

External Events are untrusted input until validated.

Adapters should validate:

- Provider authenticity where supported.
- Webhook signatures/secrets.
- Required provider fields.
- Allowed event/action types.
- Runtime Job references.
- Payload size limits.

Never execute arbitrary commands encoded directly by untrusted provider text.

---

# 46. Secret Handling

Webhook secrets, Discord bot tokens, Trello credentials, and runtime API keys must not appear in:

- Event payloads.
- Professional artifacts.
- Runtime Job.
- Trello card comments.
- Discord messages.
- Source control.

Authentication metadata belongs in secure configuration.

---

# 47. Event Payload Size

Event payloads should remain small.

Use references for:

- Artifacts.
- Messages.
- Interactions.
- Executions.
- Routing decisions.

Avoid copying:

- Resume files.
- JER corpora.
- Discord transcripts.
- Full JEA content.
- WCM content.

This keeps persistence and retries lightweight.

---

# 48. No-Op Events

Valid Events may result in no command.

Example:

```text
Trello visual metadata changed
```

Normalized Event may be marked:

```text
ignored
```

This is not failure.

The runtime should distinguish:

```text
ignored intentionally
```

from:

```text
failed to process
```

---

# 49. Event Reconciliation After Restart

After runtime restart:

1. Load Events with status:
   - `received`
   - `processing`
   - `retry_pending`
2. Reconcile worker ownership if necessary.
3. Resume idempotent processing.
4. Use operation keys and Runtime Job revision to avoid duplicate professional work.

An Event left in `processing` by a crashed worker must not remain permanently stuck.

---

# 50. Event Processing Lease

A future implementation may use a processing lease:

```yaml
processing:
  worker_id: WORKER-02
  lease_expires_at: ...
```

This is an implementation detail, not required for V0.1 architecture.

The architectural requirement is:

> Abandoned Event processing must be recoverable.

---

# 51. Event Ordering Example

Two Events arrive:

```text
EVT-A human_input_received
EVT-B cancel_requested
```

Correct behavior cannot rely purely on timestamps.

The runtime should coordinate mutation through current Runtime Job state and per-job concurrency.

If cancellation commits first, later interaction processing must observe:

```text
lifecycle == cancelled
```

and safely stop.

---

Each Event should support structured logs including:

```text
event_id

job_id
provider
correlation_id
causation_id
processing_status
attempt_count
criticality
```

Logs should not require embedding full professional content.

# 54. Event Model Design Boundary

The Event Model should answer:

- What happened?
- Where did the event originate?
- Which Runtime Job does it affect?
- What caused it?
- What runtime activity is correlated with it?
- Is it workflow critical?
- Has it been processed?
- Does processing need retry/manual review?

It should not answer:

- Whether professional evidence is strong.
- Whether a candidate qualifies.
- What a resume should say.
- Which agent is professionally responsible.
- What factual conclusion should be reached.

---

# 55. V0.1 Acceptance Criteria

The Event Model is acceptable when:

- [ ] Events and Commands are distinct concepts.
- [ ] One normalized internal Event envelope exists.
- [ ] External Trello/Discord payloads are normalized by adapters.
- [ ] Events are persisted before asynchronous processing.
- [ ] At-least-once delivery is supported safely.
- [ ] Provider event deduplication exists conceptually.
- [ ] Event processing is idempotent.
- [ ] Operation-key idempotency provides additional duplicate protection.
- [ ] Event payloads reference artifacts rather than embed them.
- [ ] Human-input Events reference Interaction/Message records.
- [ ] Event processing supports retry and dead-letter states.
- [ ] Workflow-critical and integration-only failures are distinguished.
- [ ] Integration-only failure does not roll back professional state.
- [ ] Per-job ordering/concurrency is protected without requiring global ordering.
- [ ] Trello remains primarily a projection.
- [ ] Arbitrary Trello card movement is not authoritative workflow state.
- [ ] Discord input cannot directly mutate professional evidence.
- [ ] Event history supports causation and correlation audit.
- [ ] Runtime restart can recover incomplete Event processing.
- [ ] Complete/cancelled Runtime Job state is respected during Event processing.
- [ ] Secrets and large professional content remain outside Event payloads.
